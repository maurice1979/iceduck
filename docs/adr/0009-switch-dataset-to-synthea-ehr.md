# ADR-0009: Switch demo dataset from Olist e-commerce to Synthea synthetic EHR data

Status: Accepted
Date: 2026-09-16

## Context

The project originally planned to use the Olist Brazilian E-Commerce dataset (Kaggle) for its bronze/silver/gold demo. Before any ingestion code was built against it, the project owner asked to explore whether a medical dataset (patient/doctor/hospital/medication records) was available instead, since nothing had been built against Olist's schema yet and the swap would be cheap.

Two real candidates were evaluated on Kaggle:

- **`mshamoonbutt/hospital-management-system`** — MIT licensed, a well-designed normalized relational schema (14 tables: Department, Room, Doctor, Nurse, Ward, Bed, Patients, Appointment, MedicalRecord, SurgeryRecord, StaffShift, etc.), reasonable data volume (roughly 500-1000 rows per core table). Ships as a single SQL dump (`.sql`) plus an Excel file — not CSV-native, so using it would mean parsing/restoring the SQL dump before it could enter IceDuck's raw CSV landing step. Medications aren't a separate table — they're a free-text column (`treatment`) on `MedicalRecord`.
- **`lucague/hospital-ehr-data-1171-patients-15-tables`** — Apache-2.0 licensed, synthetic EHR data generated by **Synthea™** (MITRE Corporation's open-source patient population simulator, widely used in healthcare informatics research). Ships as 15 clean, CSV-native tables (`patients`, `providers`, `organizations`, `encounters`, `medications`, `conditions`, `procedures`, `immunizations`, `allergies`, `careplans`, `devices`, `imaging_studies`, `payers`, `payer_transitions`, `observations`), linked by UUID foreign keys, explicitly described by its author as "a star pattern centred on *encounters*." Uses real clinical coding standards (SNOMED-CT, LOINC, RxNorm, ICD-10, NDC, CVX). Because it's entirely synthetic, there's no patient-privacy risk, no IRB approval, no data use agreement, and no restriction on publishing derived data or notebooks — a meaningful advantage over any dataset built from real records.

## Decision

Switch to **`lucague/hospital-ehr-data-1171-patients-15-tables`**. It's CSV-native (no format-conversion step needed, unlike the SQL-dump alternative), has an explicit `medications` table (the other candidate doesn't), and its star-schema shape maps directly onto the medallion/dimensional-modeling goal that's the whole point of this project.

**Entity scope, this phase**: 6 of the dataset's 15 tables — `patients`, `providers` (doctors), `organizations` (hospitals), `medications`, `encounters` (the central fact, links everything), `conditions` (diagnoses). This directly matches the "patients, doctors, hospitals, medications" brief, plus `encounters` and `conditions` since they're needed for a real relational demo and are core to "medical records."

**Deferred, not built now**: `payers`/`payer_transitions` (insurance, tangential to the core story), `observations` (by far the largest table at ~300k rows — labs/vitals, not needed for this scope), `procedures`, `immunizations`, `allergies`, `careplans`, `devices`, `imaging_studies`. Revisit if the project wants a richer clinical picture later — nothing about this decision blocks that, the same dataset already has them.

**Fixtures**: `sample_data/health/download.py` pulls the full 6 tables via the `kaggle` Python package (auto-authenticates from `~/.kaggle/access_token`), then generates a small, **referential-integrity-aware** committed subset in `sample_data/health/fixtures/`: the first 15 patients, every `encounters`/`medications`/`conditions` row belonging to them, and every `providers`/`organizations` row those encounters actually reference — not independent `head -N` per file, which would produce non-joining foreign keys. Tested sizing: 15 patients → 358 encounters, 124 medications, 73 conditions, 32 providers, 32 organizations (~650 rows, ~180KB total).

## Consequences

- **Dimensional model gets redesigned** (was: `dim_customer`/`dim_seller`/`dim_product`/`dim_date`/`dim_geolocation` + `fct_orders`/`fct_order_items`/`fct_payments`/`fct_reviews`; now: `dim_patient`/`dim_provider`/`dim_organization`/`dim_date` + `fct_encounters`/`fct_medications`/`fct_conditions`) — see the updated Model Layout in `docs/plans/0001-lakehouse-architecture-outline.md`.
- **Bigger, more realistic scale than Olist** for the full dataset (~472k rows across all 15 tables vs. Olist's ~100k orders) — the fixtures subset stays small regardless, so this doesn't affect fast local demo runs.
- **New dependency**: `kaggle` (Python package) is now a project dependency, needed for `sample_data/health/download.py`. Only used for the one-time full-dataset pull, not by the ongoing pipeline.
- **No working code had to be rewritten** — the swap happened before any ingestion/dbt code existed against Olist, so this ADR only had to update planning docs (`README.md`, `CLAUDE.md`, `docs/plans/0001-lakehouse-architecture-outline.md`) plus build the new `sample_data/health/` fixtures and `iceduck s3-upload-raw`, per Build Order step 4.
- **Genuinely zero privacy/compliance surface** — worth stating plainly since it's a real, not just incidental, advantage of Synthea data over any dataset containing real (even anonymized) patient records: fully synthetic, safe to commit fixtures and publish freely.
