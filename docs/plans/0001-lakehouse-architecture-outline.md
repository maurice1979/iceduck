## Context

**IceDuck** is a Data Engineer portfolio piece demonstrating a modern, from-scratch lakehouse built entirely on open-source libraries: **dbt, DuckDB, Floci (AWS emulator), OpenTofu, and Docker**. The name reflects the core of the stack: **Ice**berg (the table format) on **Duck**DB (the query engine). The project should be AWS-compatible (runnable against real AWS with minimal changes) while running fully locally against an emulator, and gives practice with OpenTofu/Terraform-style IaC.

DuckLake was originally considered but is **explicitly dropped**. The priority instead is a genuinely **modern lakehouse architecture**, which points to an open table format (ACID, schema evolution, time travel) rather than plain Parquet. Research confirmed **Apache Iceberg on AWS Glue Data Catalog** is achievable with the remaining non-negotiable stack: `dbt-duckdb` has experimental native support for persisting Iceberg tables directly into a Glue catalog (via the `dbt-duckdb[glue]` extra and dbt's newer `catalogs.yml` mechanism), and DuckDB itself can attach to Glue as an Iceberg REST-compatible catalog. This removes the need for any separate catalog database (no Postgres, no DuckLake) — **Glue becomes the single catalog for the entire medallion architecture**. Because this Glue-Iceberg integration is labeled experimental, verify it early with a spike, with a mature fallback (`pyiceberg`'s `GlueCatalog`, pointed at floci) ready if the native path proves unstable.

Decisions:
- **Project name**: IceDuck (package name `iceduck`, CLI command `iceduck`).
- **AWS emulator**: Floci (https://github.com/floci-io/floci) — MIT-licensed, lightweight LocalStack alternative, Docker-based, emulates S3/Glue/Athena/IAM, drop-in AWS SDK/CLI/IaC compatible.
- **Table format & catalog**: Apache Iceberg tables for bronze/silver/gold, all registered in AWS Glue Data Catalog (emulated via floci) — no DuckLake, no separate metadata database.
- **Dataset**: synthetic EHR data generated by Synthea™ (Kaggle: `lucague/hospital-ehr-data-1171-patients-15-tables`) — patients, providers, organizations, medications, encounters, conditions (see [ADR-0009](../adr/0009-switch-dataset-to-synthea-ehr.md); originally planned as Olist Brazilian E-Commerce, switched before any ingestion code existed against it).
- **Orchestration**: none — a Makefile + a small Python CLI (`click`) drives steps in order. No Dagster/Airflow.
- **CI/CD**: out of scope for now (tracked in `docs/TODO.md`).
- **Package management**: `uv`.

## Architecture

Single catalog, three Iceberg-backed medallion layers, one storage bucket:

| Layer | Format | Catalog | Storage |
|---|---|---|---|
| **raw** | CSV (landing only, not a table) | — | `s3://<bucket>/raw/<entity>/` (floci S3) |
| **bronze** | Iceberg | AWS Glue DB `iceduck_bronze` (emulated) | `s3://<bucket>/warehouse/bronze/<table>/` |
| **silver** | Iceberg | AWS Glue DB `iceduck_silver` (emulated) | `s3://<bucket>/warehouse/silver/<table>/` |
| **gold** | Iceberg | AWS Glue DB `iceduck_gold` (emulated) | `s3://<bucket>/warehouse/gold/<table>/` |

Raw EHR CSVs (patients, providers, organizations, medications, encounters, conditions) land in floci S3 first. A Python ingestion step loads each entity into a bronze Iceberg table via `pyiceberg`'s `GlueCatalog` (pointed at floci) — chosen over the experimental DuckDB-Iceberg write path for this first, most foundational write. From there, **dbt** (via `dbt-duckdb`, attached to the Glue catalog through `catalogs.yml`/`profiles.yml`) builds staging/intermediate models into silver and marts into gold, with every model materialized as a genuine Iceberg table in its respective Glue database. Because a real Iceberg table is queryable by any Iceberg-aware engine, the same gold tables are independently readable via emulated **Athena** (proving AWS-native, multi-engine interoperability) as well as by a fresh DuckDB session. OpenTofu provisions all AWS infrastructure (S3 bucket, IAM, three Glue databases, Athena workgroup) against floci.

**Risk & fallback (verify early, Phase 3 below):** if dbt-duckdb's native Glue-Iceberg materialization proves unstable against floci during the spike, fall back to: dbt-duckdb writes external Parquet, then a small `iceberg_publish.py` script uses `pyiceberg`'s `GlueCatalog` to create/write true Iceberg tables from that Parquet into the appropriate Glue database. Toggle via `ICEBERG_WRITE_MODE=duckdb_native|pyiceberg` in `.env`. Either path produces the same end state (real Iceberg tables in Glue).

## Key Design Points

- **Docker Compose** (`docker/compose.yaml`): just `floci` (image `floci/floci:latest`, port 4566, **`FLOCI_STORAGE_MODE=persistent`** — the default is in-memory and wipes S3/Glue state on restart). No Postgres — there is no separate catalog database to run.
- **OpenTofu** (`infra/tofu/`): `aws` provider pointed at floci via `endpoints{}` block with static `test`/`test` credentials; provisions one S3 bucket (+ `raw/`, `warehouse/`, `athena-results/` prefixes), an IAM role+policy for Athena/Glue access, **three** Glue databases (`iceduck_bronze`, `iceduck_silver`, `iceduck_gold`), and an Athena workgroup with a results location. No Glue crawler needed — schemas are known at write time (dbt/pyiceberg create tables explicitly).
- **Bronze ingestion**: `sample_data/health/download.py` pulls the Kaggle dataset (small committed `fixtures/` subset for fast demo, generated with referential integrity — see ADR-0009); `iceduck s3-upload-raw` uploads CSVs to floci-S3 `raw/`; `iceduck ingest[-all]` reads each `products/*.yml`-defined entity from `raw/` and writes it as an Iceberg table into `iceduck_bronze` via `pyiceberg`'s `GlueCatalog`.
- **dbt**: staging/intermediate materialize as Iceberg tables in `iceduck_silver`; marts materialize as Iceberg tables in `iceduck_gold`. `catalogs.yml` (or `profiles.yml`'s `catalogs:` block, depending on the installed dbt/dbt-duckdb version — verify during implementation) attaches DuckDB to Glue via `dbt-duckdb[glue]`; models set `catalog_name` per layer. `profiles.yml` is committed and fully env-driven.
- **Model layout** (EHR, see ADR-0009): staging (1 per CSV entity: `stg_patients`, `stg_providers`, `stg_organizations`, `stg_medications`, `stg_encounters`, `stg_conditions`) → marts: dims (`dim_patient`, `dim_provider`, `dim_organization`, `dim_date`) + facts (`fct_encounters` — the central fact, `fct_medications`, `fct_conditions`).
- **Spike (Phase 3, do early)**: covers *both* write paths that the pipeline depends on, since bronze ingestion uses `pyiceberg` unconditionally regardless of which mode wins for silver/gold — don't let a `pyiceberg`-against-floci failure surface as late as Phase 5. (a) Use `pyiceberg`'s `GlueCatalog` directly to create a trivial Iceberg table against floci and read it back. (b) Build one trivial dbt model materialized as Iceberg via the native `dbt-duckdb[glue]` path against floci. For both, verify: it appears correctly in `aws glue get-table`, Athena can query it, and a fresh DuckDB session re-attaching to the Glue catalog can read it back with correct data. Document both verdicts in `docs/plans/applied/`. If (a) fails, the Glue-Iceberg architecture itself needs rethinking before proceeding further; if only (b) fails, switch `ICEBERG_WRITE_MODE=pyiceberg` for dbt models.
- **Docs**: `docs/architecture.md` documents the single-catalog Iceberg-on-Glue design and the interoperability story; `docs/plans/` logs phased decisions as they're built; `docs/TODO.md` lists explicitly out-of-scope items (CI/CD, orchestrator).

## Build Order (phased, each with a verification gate)

0. Scaffold: `uv add dbt-core "dbt-duckdb[glue]" duckdb pyiceberg boto3 click pydantic-settings python-dotenv`; create `src/iceduck/`, `.env.template`. **Verify**: `uv run iceduck --help`.
1. Docker Compose up floci. **Verify**: `aws --endpoint-url ... s3 mb/ls` round-trips and survives `docker compose restart`.
2. OpenTofu apply (S3/IAM/3x Glue DB/Athena). **Verify**: `tofu apply` clean; `aws s3 ls`, `aws glue get-database` (x3), `aws athena get-work-group` all succeed.
3. **Iceberg-on-Glue spike** — both the `pyiceberg` GlueCatalog path (used unconditionally by bronze ingestion) and the native `dbt-duckdb[glue]` path (candidate for silver/gold), de-risking before building the rest. **Verify**: documented verdict in `docs/plans/applied/`; `ICEBERG_WRITE_MODE` decided.
4. Raw landing: fixtures + `s3-upload-raw`. **Verify**: `aws s3 ls s3://<bucket>/raw/patients/`. ✅ Done — see `docs/adr/0009-switch-dataset-to-synthea-ehr.md`.
5. Bronze ingestion via `pyiceberg` (`ingest-all`). **Verify**: `aws glue get-tables --database-name iceduck_bronze` lists all entities; row counts match source CSVs. ✅ Done.
6. dbt staging + intermediate → silver (Iceberg via chosen write mode). **Verify**: `dbt test` green; `aws glue get-tables --database-name iceduck_silver` populated; silver counts reconcile against bronze. ✅ Done — no intermediate layer needed (staging is already 1:1 with bronze); see [`docs/plans/0004-dbt-silver-layer.md`](0004-dbt-silver-layer.md) and [ADR-0010](../adr/0010-dbt-silver-write-and-read-mechanism.md).
7. dbt marts → gold (Iceberg). **Verify**: `aws glue get-tables --database-name iceduck_gold` shows all dims/facts with correct schemas. ✅ Done — see [`docs/plans/0005-dbt-gold-layer.md`](0005-dbt-gold-layer.md).
8. Athena + fresh-DuckDB interoperability verify. **Verify**: an Athena query against a gold fact table and a fresh DuckDB session reading the same table both return the same row count. ✅ Done — see [`docs/plans/0006-athena-duckdb-interop.md`](0006-athena-duckdb-interop.md).
9. Makefile (`demo`, `reset`, `infra-up/apply/destroy`, `ingest`, `dbt`). **Verify**: `make demo` runs unattended end-to-end on fixture data. ✅ Done — see [`docs/plans/0007-makefile-pipeline.md`](0007-makefile-pipeline.md).
10. Tests (`unit/` + `integration/` gated by `ICEDUCK_IT=1`). **Verify**: both pytest runs green.
11. Docs (README quickstart, CLAUDE.md, `docs/architecture.md`, `docs/plans/*`, `docs/TODO.md`). **Verify**: a fresh clone + README quickstart reproduces `make demo`.

## Critical Files

- `docker/compose.yaml` — floci service only
- `infra/tofu/providers.tf`, `infra/tofu/glue.tf` — floci-pointed AWS provider, 3x Glue database
- `dbt/iceduck/profiles.yml`, `dbt/iceduck/catalogs.yml`, `dbt/iceduck/dbt_project.yml` — Glue catalog attach + per-layer `catalog_name` config
- `src/iceduck/core/iceberg_catalog.py`, `src/iceduck/core/iceberg_publish.py` — pyiceberg GlueCatalog factory, fallback publish path
- `src/iceduck/core/settings.py` — canonical env var source shared by compose/tofu/CLI/dbt
- `.env.template` — single source of truth for all env var names across tools

## Verification (end-to-end, once built)

Run `docker compose -f docker/compose.yaml up -d`, `tofu -chdir=infra/tofu apply`, then `make demo`. Confirm: (1) `aws glue get-tables` on all three databases lists the expected Iceberg tables with correct schemas; (2) `aws s3 ls` on floci shows `raw/` and `warehouse/{bronze,silver,gold}/` populated with Iceberg data+metadata files; (3) an Athena query against a gold fact table and a fresh DuckDB session attached to the same Glue catalog both return matching row counts — proving genuine multi-engine interoperability on one physical table, the central claim of the "modern lakehouse" pitch.
